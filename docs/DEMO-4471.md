# Customer 4471 demo

This is the operator script for the recorded Blast Radius demonstration. All
records are synthetic. The visible request starts discovery and shadow-copy
rehearsal, but it does **not** authorise a production deletion. Only the human
Allow action at TrueForge's approval gate can release the destructive tool.

## Before recording

1. Follow `docs/SETUP.md` through agent provisioning.
2. Confirm Docker reports `postgres`, `redis`, `mcp-server`, `demo-postgres`,
   and `demo-mcp-server` healthy, and `demo-seed` exited successfully.
3. In TrueForge, confirm the OpenAI model, Daytona sandbox provider,
   `gdpr-erasure` skill, and `subject-data` connector are connected.
4. Re-provision after pulling this branch so the demo trigger in
   `packages/agent/agent.manifest.json` is applied.
5. Start a new session with the `blast-radius` agent. Do not reuse a session
   whose execution token may have expired or whose shadow snapshot is stale.

For a one-command pre-recording check, run this from `packages/agent` after
provisioning:

```bash
npm run verify:demo
```

It starts the exact demo prompt, validates every measured milestone below,
and stops with `execute_deletion` pending at the approval gate. It never
approves the action or changes production.

## Visible request

Type exactly:

> Find information on Customer 4471

The request is intentionally phrased as discovery. The demo-only agent rule
may investigate, plan, and rehearse, but production remains untouched until a
human reviews the measured plan and selects Allow.

## Expected story

### 1. Read-only discovery

The trace should show `inspect_schema`, `list_foreign_keys`,
`get_retention_policies`, and `find_subject_data` without an approval prompt.
Discovery should return summaries and counts, never row contents.

| Table | Measured rows for customer 4471 |
|---|---:|
| customers | 1 |
| addresses | 3 |
| uploads | 2 |
| support_tickets | 1 |
| audit_log | 4 |
| orders | 8 |
| order_items | 40 |
| **Total** | **59** |

The trace should also make these deliberate foreign-key behaviours visible:

- deleting a customer cascades to addresses, uploads, and orders;
- deleting an order cascades to its order items;
- deleting a customer sets the customer reference on support tickets and
  audit events to null unless those rows are explicitly removed first.

### 2. Policies and naive plan

The agent must read the policy table during this run. The canonical synthetic
demo has exactly four rows:

| Table | Basis | Retention |
|---|---|---:|
| customers | none | 0 years |
| support_tickets | none | 0 years |
| orders | tax | 7 years |
| order_items | tax | 7 years |

The first plan should attempt the literal erasure request. It should not be
sent to production. It exists to expose the real cascade in rehearsal.

### 3. Practice run one: measured conflict

The agent calls `snapshot_to_shadow`, then `rehearse_deletion`. The first
rehearsal should account for all 59 connected rows and report that deleting
the customer would destroy 8 orders and 40 order items protected by the
seven-year policy.

Expected safety result:

- production touched: **false**;
- protected rows put at risk: **48**;
- `would_be_illegal`: **true**;
- execution token: **null**.

The important line for narration is: a plan can succeed technically and still
fail the policy check.

### 4. Revised plan

Without being told table-specific answers, the agent should resolve the
measured conflict. In this schema, the clean strategy is:

| Action | Rows |
|---|---:|
| Delete addresses | 3 |
| Delete uploads | 2 |
| Delete support tickets | 1 |
| Delete audit events | 4 |
| Anonymise customer PII | 1 |
| Preserve orders | 8 |
| Preserve order items | 40 |

The customer row remains so `orders.customer_id` still resolves and its
`ON DELETE CASCADE` never fires. The columns named by the customers policy
(`email`, `full_name`, and `phone`) are overwritten instead.

### 5. Practice run two: clean result

The agent takes a fresh snapshot and rehearses the revised plan.

Expected result:

- 10 rows hard-deleted;
- 1 customer row anonymised;
- 48 protected financial rows preserved;
- 0 retention violations;
- production touched: **false**;
- one short-lived, single-use execution token issued for this exact plan.

### 6. Human-in-the-loop approval

After showing the final plan and measured counts, the agent calls
`execute_deletion` with the clean plan and its matching token. TrueForge must
pause the call and show Allow / Deny. Nothing has changed in production at
this point.

The approval view should make these numbers easy to read:

| Decision surface | Rows |
|---|---:|
| Delete | 10 |
| Anonymise | 1 |
| Preserve | 48 |
| Policy violations | 0 |

For a short recording, stop here and explain the two choices. For a complete
recording, first demonstrate Deny in a disposable session, then start a fresh
session and demonstrate Allow.

### 7. Deny path

On Deny, the agent must not replay the same execution call. Any changed plan
needs a fresh snapshot, rehearsal, and token before it can return to the gate.

### 8. Allow, verification, and receipt

On Allow, `execute_deletion` runs the approved plan in one production
transaction. The agent then verifies the resulting database state against the
approved rehearsal and produces a receipt.

Expected receipt:

- 59 connected records discovered;
- 10 records deleted;
- 1 customer identity anonymised;
- 8 orders and 40 order items preserved under the seven-year policy;
- final production state matched the approved rehearsal;
- no unapproved tables changed.

## Stop conditions

Stop the recording run without approving if any of these occurs:

- the discovered counts do not match the seeded customer;
- a tool returns row contents instead of summaries;
- the first rehearsal touches production or issues a token;
- the revised rehearsal reports a retention violation;
- the approval view does not match the clean rehearsal;
- `execute_deletion` runs before a visible human decision.

The closing line is:

> Blast Radius does not ask us to trust an agent's prediction. It measures the
> real blast radius on a disposable copy, binds approval to that exact plan,
> and keeps a human in control of the irreversible action.
